> 建档：2026-10-12。依据：v1.3 workflow JSON（12节点）+ 命令模板要素提炼.md（33份语料统计）+ 2026-10-12 讨论定稿。
> 定位：三个可用性机制的落地方案——①对话流收敛追问；②节点故障旁路；③apifox批量问答对生成与校验。
> 状态：方案文档，未执行。首个闭环实验见文末。
> **v0.2修订（2026-10-13）**：v1.4 导入平台失败（已定位结构病因，见附录B）；实测 MCP 节点故障直接断流返回"SSE调用失败"，画布内 Ifs 无法感知 MCP 故障；v1.5 已删除 MCP 导出旁路分支。决策修订详见第2章。

## 0. 修订记录（2026-10-13，替代10-12部分决策）

1. **MCP 旁路降级撤回**：原方案"Word文档生成失败→Ifs判断→兜底end"不可行。实测 MCP 节点错误后流程直接中断（SSE调用失败），错误信息不进入下游变量，Ifs 判断节点拿不到 MCP 的失败状态——画布内旁路在当前平台版本上不存在实现路径。
2. **MCP 不做旁路是合理终态，不是妥协**：接入的 MCP（如 Word 导出）背后是稳定运行的系统服务；真正的业务系统对接（取运行图数据等）本来就不该也无法用画布代码块复刻。结论：**MCP 挂点一律按 A 类（断则终止）管理**，可用性靠服务端监控告警保障，不靠画布旁路。原第2章"Word文档生成 A（核心输出）终止"的分级恰好不变，删掉的只是画布内 Ifs 判断分支这层实现幻觉。
3. **"能用代码块实现的，考虑封装成独立子智能体（skill 式沉淀）而非塞进画布"**：确定性逻辑（校验、拼装、槽位判定）可进画布 Code 节点；需要独立编排/复用的能力封装成子智能体（集群已有 Word文档导出/PDF和Word文档读取 等子智能体先例）。
4. **追问机制以"轮次调用"为准**（张谦口径）：第一轮跑完输出《编制信息确认单》提示缺失；用户补齐后**第二轮全量重跑**，不是画布内等待补充。v1.4 的澄清判定 Code 节点+多end 结构与该机制兼容（确认单→结束-澄清追问 end），保留。第二轮重跑时模型需把上一轮补充信息并入输入——对话上下文由平台 chatflow 会话承载，画布不用改。

## 1. 槽位表（问题一：追问收敛的依据）

对话流放在「用户意图识别」与「运作命令生成」分支之间。缺槽→一轮合并式追问→仍缺按默认口径继续（输出标注假设）。

### 1.1 必填槽与默认口径

| 槽位 | 必填性 | 默认口径 | 缺失处理 |
|---|---|---|---|
| 起始日期 | 必填 | 无默认 | 追问1轮，仍缺→终止 |
| 命令号N | 必填 | 无默认 | 追问1轮，仍缺→终止 |
| 各线执行运行图编号（8线） | 必填 | **无默认，编不得** | 追问1轮，仍缺→终止（A类红线） |
| 运作时间段条件 | 必填 | 逢工作日/逢周末按历史同类命令推断，标注假设 | 可默认 |
| 运营时间 | 必填 | 参照上期命令同线同图号 | 可默认（标注"参照上期"） |
| 备用车安排 | 可选 | 图定备车 | 可默认 |
| 风险项点 | 可选 | 无→变体B（三章） | 有→变体A（四章） |
| 表尾注类型 | 可选 | 新编图→"加粗为新编"；无变更→省略 | 可默认 |
| 发文字号 | **永不追问** | 占位符〔2025〕___号 | 人工补（铁律，非函数关系） |

### 1.2 追问预算

- 最多1轮，合并式提问（一次问全所有缺失必填槽，禁止挤牙膏式逐个问）。
- 用户回复后仍缺：可默认槽走默认并标注；无默认槽（日期/命令号/图号）→终止并说明缺什么。
- 远期：运行图编号、运营时间的正源是运输计划/运行图编制智能体输出，追问用户只是v1兜底。

## 2. 节点故障旁路（问题二：v0.2 修订）

v1.3 现无MCP挂点，先对现有节点做分级；接运行图数据MCP时再补挂点表分级列。

**v0.2 结论：MCP 节点不做画布内旁路。** 实测（2026-10-13）：MCP 节点错误后流程直接中断，前端收到"SSE调用失败"，错误状态不写入任何下游变量——Ifs 分支判断节点根本拿不到 MCP 是否失败的信息，原方案 v1.4 的"导出成功？→结束-导出兜底"分支是无效设计，v1.5 已删除。理由升维：接入的 MCP 是稳定运行系统服务的通道，真业务对接本来就不能用画布代码块复刻；能用纯代码实现且需复用的，封装成子智能体（集群已有 Word文档导出/文档读取 先例）。MCP 可用性靠服务端监控告警，不靠画布兜底。

| 节点/环节 | 级别 | 旁路方案 | 输出标注 |
|---|---|---|---|
| 历史检索+RAG重排器 | B（有替代） | 退化为纯模板生成（依据=命令模板要素提炼.md 的33份统计固定句式），无few-shot样例 | "未参照历史样例" |
| 知识库检索+RAG重排器 | B（有替代） | 退化为无知识库问答/提示知识检索暂不可用 | "知识检索降级" |
| 用户意图识别 | A | 终止，提示人工选择分支 | — |
| Word文档生成/地址提取 | A（核心输出） | **画布内无旁路（v0.2实测确认），断则终止**；可用性靠MCP服务端监控告警 | — |
| 运行图数据MCP（将来） | A | 数据编不得，终止；不做画布旁路（同上） | — |

> 前置实验（2026-10-13已完成）：断开MCP/知识库节点观察——MCP故障直接断流（SSE调用失败），无旁路可言；RetrieverV2 故障行为待同类实验确认（若同样断流，B类旁路也只在"返回空结果但节点成功"场景生效）。
- 降级不静默：所有旁路输出必须在文末/答复中带数据性质标注（实测/快照/模板退化/默认假设）。

### 3.3 断言分层（混用会出假结果）

代码断言（apifox原生，数值/格式类）：
- 固定句式逐字匹配：「X年X月X日起至另有通知时止执行的列车运行图如下：」「各线路ATS系统中仅留存下列运行图」
- 表格列头：线别|运作时间段|执行运行图|运营时间|备用车安排；8线固定顺序
- 变体章节结构（A四章/B三章）
- 部门口径=「自动化中心」（2025年5月后）
- 文号占位符：出现编造文号→**一票否决fail**
- 图号格式：Z/T/Y+5位数字，线路代号前2位正确

judge断言（外挂python或apifox后置脚本调LLM-as-judge，judge≠被测模型）：
- 调图项点描述与提供风险项点一致性
- 新写注意事项条目风格与历史同类一致（按调图缘由类型检索同类）
- 表尾注选择正确性
- judge提示词锚定：数值以上游节点/入参为准，不自行判数

## 附录C：两层架构定案 + 对话流 v0.2（2026-10-13）

**架构决定**：采用张谦标准两层模式——对话流(chatflow)做薄入口（意图识别+输出渲染），重逻辑下沉到工作流(agent, WorkflowApp/WorkflowSubGraph 调用)，通用能力复用集群子智能体（Word文档导出等）。理由：①与"轮次调用"追问机制天然对齐（对话流会话承载上下文，第一轮确认单→补充→第二轮重跑）；②apifox批量测试直接打工作流API，断言干净；③与集群其余智能体同构。代价：导入有时序（先子工作流后对话流），跨环境迁移后 patent_id 引用需手工重绑。

**对话流 v0.2**（运作命令生成对话流_v0.2.json，基于用户平台手建框架补提示词，未动画布骨架）：
- 意图识别-1：true→工作流子模块（运作命令生成）；false→知识库问答分支。提示词含轮次追问路由规则（回复"确认"/补充槽位信息必判生成意图，use_history=true）。
- 大模型-1（问答+范围外接待合一，不新增节点）：类型一=域内知识问答（沿用v1.3问答提示词）；类型二=范围外指引——先列集群智能体路由表（沿线活动/节假日/新线/运行图编制/运行图评估/客流分析/运输计划/多网融合），属新需求/优化建议的输出可复制登记条目模板（智能体/类型/描述/提出人）供用户贴到部门智能表格。
- 注意：范围外指引依赖大模型LLM自判类型，检索分支对纯范围外输入可能召回弱相关内容——若误答，下一步在意图识别加第三个意图"范围外"单独分支（v0.3候选）。

## 附录H：v2.0 确定性流水线蓝图 + 护网MCP降级（2026-10-13）

**方向定案**（用户提出，张谦模式验证可行）：33份真实语料足以支撑全量生成；第一阶段=智能体生成全量草稿+人工微调校对，规则完善后逐步移交智能体主导。改造=把"一个LLM写全文"换成张谦式确定性流水线：**表格/编号/固定句式/闭合校验全Code节点，LLM只写注意事项条目文字**（12节点：C1槽位抽取→I1槽位齐？→C2确认单组装(Code替代LLM)/L1条目生成(LLM)→C3确定性组装→C4终检→I2导出开关→MCP）。详见《工作流v2.0节点蓝图.md》（含全部节点代码+提示词，本地冒烟已过）。

**护网行动MCP降级方案**：MCP断流不可事后兜底（10-13实测），降级必须**事前开关**——画布加环境变量 export_enabled（默认true），I2 Ifs 判断后才走 Word文档生成 节点；护网期改 false 则跳过MCP直接输出纯md_text（download_url为空）。护网结束改回即恢复，不动连线。二期可评估HTTP节点调内网转换服务（张谦有HTTP先例）。

**新增第4输出变量 check_report**（C4终检报告，把apifox断言搬进流程内：标题规范/通知体残留/表头/8线/空图号/图号线路代号/发文字号红线），第一阶段人工微调时按报告逐项校对，终检不阻断。

## 附录F：对话流 v0.3 + 命令规律结论（2026-10-13）

**对话流 v0.3**（运作命令生成对话流_v0.3.json）：
1. 输出模板首次填入真实变量引用（clarify_text/md_text/download_url/大模型text 四段式，工作流子模块已绑定 patent 32203c44 的 v1.7 单end工作流）。

**33份语料规律（命令到底怎么来的）**：
- 2025年33号命令，平均1-3周一发；相邻命令工作日图**零变更**的13/32（40%）——这批只调运作时段/节假日窗口/沿线活动行，底图沿用上期。
- 全网换图（7-8/8线）集中在季节节点：3-01（7号）、4-27（13号）、6-13（18号夏季）、8-01（23号）、9-01（26号）、9-28（29号Q4）。
- 结论：**上期命令为底（默认）+ 季节性全网换图为节点（显式给全套新图号）**。智能体默认口径=沿用上期现行图号+叠加本期特殊时段行，与槽位表"运营时间参照上期"一致；季节性换图期由用户显式提供新图号，不靠猜。

**平台约束**：对话流的 WorkflowSubGraph/WorkflowApp 节点只暴露**一个**结束节点的输出变量——多end时对话流侧无法选全输出（用户实测发现）。v1.6 双end→v1.7 单end合并：

- 结束节点统一输出三变量：`md_text`（正式命令正文）、`download_url`（Word下载地址）、`clarify_text`（《编制信息确认单》文本）——均绑定运作命令生成.text 或下游输出；未走的分支输出为空。
- 拓扑：开始 → 历史运作命令检索 → RAG重排器-1 → 运作命令生成 → 澄清判定 → 需澄清？ → true=结束 / false=Word文档生成(MCP) → Word地址提取 → 结束（9节点9边）。
- 对话流输出模板相应改为按变量判空渲染：md_text 有值渲染正文+下载地址；clarify_text 有值渲染确认单。若输出模板不支持条件判断，简化为三变量依次输出（空值平台渲染为空）。
- 结论：内层工作流设计准则——**单end+全量输出变量**，分支差异用变量空值表达，不再用多end。

## 附录B：v1.4 导入失败病因定位（2026-10-13）

1. **主要嫌疑：新增 Ifs 节点缺 `config__parameters` 字段**。v1.4 的"需澄清？/导出成功？"两个 Ifs 节点均无该字段，而平台导出的 Ifs 节点都有（内容含 `payload__if_else` 参数声明）。Code 节点（澄清判定）字段集完整无偏差。v1.5 已补齐（从平台样例原样复制）。
2. 次要观察：v1.4 对旧"结束"节点做了改名+裁剪 input_shape（4→2）、position 类型 float→int——与平台导出件存在类型差异，但多end结构本身平台支持（YSJQ-0007 有4个end），非病因主嫌。
